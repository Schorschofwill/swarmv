Eine Probe losschicken

Reiht {{ task_name }} ein — einen Task, der auf Ansage wartet, rechnet oder scheitert. Er muss im Worker bekannt sein; sonst liegt die Probe in der Queue und wird nie aufgegriffen. Ein Import im eigenen Task-Modul genügt: from swarmq_dashboard.probe import ProbeTask — --module lässt sich nicht zweimal angeben.

Sie entscheidet, welcher Worker die Probe bekommt — io wartende Arbeit, cpu rechnende.
Höchstens {{ max_anzahl }}. Eine einzelne Probe steht nie in der Queue — für einen sichtbaren Rückstau braucht es mehrere.
Belegt einen Slot, ohne die CPU zu belasten. Höchstens {{ max_dauer|int }} s.
Belastet die CPU wirklich — die ehrliche Probe für den Rechen-Pool, wo Warten nur einen Slot blockiert.
Geht über den Scheduler statt direkt an den Broker.
Statt einer Verzögerung — nie beides zugleich.
Innerhalb der Frist gibt eine zweite gleiche Einreihung die Kennung der ersten zurück, ohne neue Arbeit.
Steht in den Argumenten und im Fehlertext — der Faden, an dem der Versuch später in der Task-Liste hängt.

Was hier nicht steht

Fristen, Wiederholungen, Ratenbegrenzung, Sperren, Verfall und Priorität gehören zur TaskInfo des Tasks und gelten für jede Einreihung gleich — die Bibliothek nimmt sie bei schedule() nicht entgegen. Felder dafür anzubieten hieße, eine Wirkung zu versprechen, die es nicht gibt. Wer sie ausprobieren will, ändert sie an swarmq_dashboard.probe.ProbeTask und startet die Worker neu.
